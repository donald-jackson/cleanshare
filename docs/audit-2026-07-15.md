# CleanShare — Security & Submission-Readiness Audit

**Date:** 2026-07-15
**Scope:** whole repository — cleaning engine, verifier, share extension, host app,
CI privacy gates, Info.plists/entitlements, and App Store submission package.
**Method:** manual review + empirical reproduction on the iOS Simulator against the
dirty fixtures, with regression tests added for every fix (TDD).

CleanShare's entire value proposition is a single promise: *nothing identifying leaves
your device.* The audit therefore treated any path where metadata could survive cleaning
**and still be reported as success** as the highest-severity class of bug — a silent
failure of the core guarantee is worse than a crash, because the user trusts a lie.

---

## Verdict

The app had **one critical fail-open in the video path** and a **matching blind spot in
the verifier** that between them meant a cleaned video's GPS could survive and the pipeline
would still report success. Both are fixed and now proven by tests. Separately, the app was
**not submittable** as-is: it was missing the `PrivacyInfo.xcprivacy` manifests Apple has
required since 2024 (automatic rejection ITMS-91053). That is fixed too.

After the fixes: **35/35 core tests pass** (6 fuzz tests skipped when the corpus isn't
generated), `make verify-strip` passes end-to-end **including video**, the full app builds,
the privacy manifests bundle into the `.app`, and the app runs on-device (verified on
simulator, screenshots captured from the real UI).

## Critical findings

### C-1 — Video path failed open: cleaned video never verified

`MetadataAuditor.audit()` (the synchronous image auditor) returns `[]` unconditionally for
`.mp4`, `.mov`, and `.livePhoto` kinds — it only understands `CGImageSource`. The video
cleaner (`AVPassthroughCleaner`) finished writing the passthrough output and returned a
success receipt **without ever calling the video-aware auditor**. Net effect: the
"fail-closed on any residue" guarantee — the thing that makes CleanShare trustworthy — did
not exist for video at all. A video whose GPS survived the passthrough would be reported as
cleaned.

Reproduced by cleaning a dirty fixture and observing its GPS box survive with no error
raised.

**Fix** — `Engine/AVPassthroughCleaner.swift`: after `finishWriting` and the status check,
the output is audited and destroyed on any residue:

```swift
let leaked = try await MetadataAuditor.auditVideo(url: output, allowing: [])
guard leaked.isEmpty else {
    try? FileManager.default.removeItem(at: output)
    throw CleanerError.leakDetected(keys: leaked)
}
```

### C-2 — The verifier was blind to where video GPS actually lives

Fixing C-1 is not enough, because the obvious way to audit a video —
`AVAsset.metadata` / `.commonMetadata` / `availableMetadataFormats` — **does not surface
the 3GPP location boxes**. GPS in QuickTime/MP4 lives in `udta` boxes named `loci`, `©xyz`
(0xA9 xyz), or `gps ` under `moov/udta` or `moov/trak/udta`, and AVFoundation silently
omits them from its metadata APIs. An auditor built only on AVFoundation would pass a file
that still carries coordinates.

**Fix** — `Verification/MetadataAuditor.swift`, rewritten to two layers:

1. **Allowlist-inverted AVFoundation scan** — collect items from `.commonMetadata`,
   `.metadata`, every `availableMetadataFormats`, and each track's `.metadata`, then flag
   **any** identifier not on a tiny explicit allowlist, plus any timed-metadata track.
   (Previously it looked only for a known-bad denylist, so anything unanticipated slipped
   through.)
2. **Raw MP4 box-tree parse** — `locationBoxes(in:)` opens the file with a `FileHandle`,
   walks the `moov` box tree (skipping `mdat` so it never reads pixel data into memory),
   and flags the sensitive `udta` leaves `loci` / `©xyz` / `gps `.

Care was taken **not** to false-positive on the `creation_time` that `AVAssetWriter`
stamps into the `mvhd`/`tkhd`/`mdhd` **headers** — those are structural fields, not
`AVMetadataItem`s, and are not user-identifying location/author data. They are correctly
left unflagged (confirmed by test).

`AVPassthroughCleaner` and `LivePhotoCleaner` both call this auditor and fail closed.

## High findings

### H-1 — Missing privacy manifests (App Store blocker)

Since spring 2024, Apple auto-rejects (ITMS-91053) any app that uses a "required-reason
API" without declaring it in a `PrivacyInfo.xcprivacy` manifest. CleanShare uses
`UserDefaults` (via the app group) and file-timestamp APIs, and shipped **no manifest** in
either target. It would have bounced on upload.

**Fix** — created `App/Resources/PrivacyInfo.xcprivacy` and
`ShareExtension/PrivacyInfo.xcprivacy`, each declaring:

- `NSPrivacyTracking = false`, empty tracking domains, empty collected-data types
  (truthful: CleanShare collects nothing — matches `docs/app-store-privacy.md`).
- Required-reason declarations: `NSPrivacyAccessedAPICategoryUserDefaults` → `1C8F.1`
  (app-group access) and `…FileTimestamp` → `C617.1`.

Verified they bundle into the built `.app` and the `.appex`.

### H-2 — Live Photo re-injection wasn't re-verified

`LivePhotoCleaner` re-injects the required `com.apple.quicktime.content.identifier` to keep
the still+video paired after cleaning. It did this **after** the audit, so the injection
step itself was unverified — a bug there could reintroduce more than the one allowed
identifier. **Fix** — re-audit after each injection (still image with the allowed keys, the
video allowing only the content-identifier), throwing `leakDetected` on anything else.

## Medium findings

### M-1 — Path traversal via the handoff token

`HandoffURL.handoffToken` accepted any string from `cleanshare://handoff?t=<token>`, and
that token is used to locate the job directory. A crafted value (`../../…`) could point
outside the workspace. **Fix** — the token is now required to parse as a `UUID`
(`UUID(uuidString:) != nil`); anything else is rejected. Regression test added.

### M-2 — Extension failed open on an empty result

If cleaning yielded **zero** receipts, `ShareViewController` still proceeded to the
"cleaned & ready" hand-off. **Fix** — a guard now drives an explicit `.failed` state (new
`failedView` in `CleaningProgressView`) and cancels the extension request instead of
implying success.

### M-3 — The "no network" claim wasn't mechanically enforced

`docs/` promise "no network, verified by CI," but `scripts/check-no-trackers.sh` only
grepped for third-party SDK names — it never scanned for networking symbols, and it wasn't
even a required PR step. **Fix** — the script now also fails on
`URLSession|URLRequest|NWConnection|CFStream|getaddrinfo|Network\.framework` (outside the
`NetworkSilenceTests` that assert silence), and it's wired into `.github/workflows/pr.yml`
and a `make check-trackers` target.

### M-4 — Inspector reported false "already clean"

The in-app "Inspect a photo" feature is a trust surface — if it says a photo is clean,
users believe it. It skipped PNG text chunks (`Author`, `Copyright`, `Software`,
`CreationTime`, …) and several MakerNote groups (Sony, Minolta), so identifying data could
be present and reported as absent. **Fix** — `MetadataInspector` now parses PNG text,
covers Sony/Minolta MakerNotes, and runs the same video location-box scan as the auditor.

## Low findings / hardening

- **L-1 Orphaned-job sweep** — abandoned cleaning jobs accumulated in the shared app-group
  container. Added `HandoffRouter.sweepExpiredJobs()` (10-minute TTL) run on launch and on
  foreground.
- **L-2 ATS lockdown** — added `NSAppTransportSecurity` with `NSAllowsArbitraryLoads=false`
  to both Info.plists. The app makes no network calls; this makes any *accidental* future
  one fail loudly rather than silently succeed.
- **L-3 Marketing/link correctness** — the real repo is `github.com/donald-jackson/cleanshare`,
  but ~10 marketing/landing files pointed at `<placeholder>` or `cleanshare/cleanshare`; the
  support URL 404'd; the AASA `appID` still read `<placeholder>`. Fixed the URLs across
  marketing, created `marketing/landing/support.html`, and set the AASA appID to
  `<TEAM_ID>.solutions.ddj.cleanshare` (Team ID still a documented human substitution).

## What remains — human-only

None of these are things an agent can do; all are tracked in
[`docs/manual-steps.md`](./manual-steps.md):

1. **Apple Developer Program enrollment** ($99/yr) → Team ID.
2. **Register bundle IDs** (`solutions.ddj.cleanshare` + `.ShareExtension`) and the
   App Group; create the App Store Connect app record.
3. **Fastlane Match** — private signing repo + run `match appstore` locally once; add
   `MATCH_*` / `ASC_*` / `FASTLANE_*` to the GitHub `release` environment secrets.
4. **Domain + DNS** — buy `cleanshare.dev`, point A records at GitHub Pages, enable the
   custom domain, and **substitute the real Team ID** into the AASA file before deploying.
5. **Submit the App Privacy questionnaire** — every category "No".
6. **Fill reviewer PII** — `fastlane/metadata/review_information/{first_name,last_name,email_address,phone_number}.txt`.
7. **Commission the real app icon** — the committed icon is a "CS" wordmark placeholder.

## Honest caveat — pre-existing lint/format debt

`RootView.swift`, `OnboardingView.swift`, and `MetadataInspectionView.swift` fail
`swiftlint --strict` / `swiftformat --lint` **at HEAD, independent of this audit** (proven
because `RootView.swift` was never touched here). I did **not** sweep the whole tree into
strict-clean — that is unbounded and out of scope for a security/submission audit, and it
risks churn in files unrelated to the findings. Flagging it so it's a deliberate decision,
not an oversight: run `swiftformat .` + `swiftlint --fix` before the strict CI gate goes
green on these files.

## How to reproduce the green state

```bash
cd Packages/CleanShareCore && swift test          # 35 pass, 0 fail, 6 fuzz skipped
make verify-strip                                  # cleans fixtures, asserts no residue (incl. video)
bash scripts/check-no-trackers.sh                  # no network / no third-party SDK symbols
xcodebuild -project CleanShare.xcodeproj -scheme CleanShare \
  -destination 'generic/platform=iOS Simulator' build \
  CODE_SIGN_IDENTITY="" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=NO
```

All changes are uncommitted on `main` — review the diff, then commit on a branch when ready
(no commit was made automatically).
